# 29 · JPA and Hibernate fundamentals

> **Run the code for this lesson**
> ```bash
> mvn -f Spring/05-data-access-with-spring-data-jpa/29-jpa-and-hibernate-fundamentals spring-boot:run
> ```
> Watch the `Hibernate:` blocks in the console — that log **is** the lesson.

This section needs a real database. **H2** — a real SQL database that runs in-process,
in memory, with zero install beyond the JDK already required for this whole stack — is
what every lesson through 36 uses, so nothing new to set up is needed until lesson 37
connects to an actual server.

---

## 1. JPA is a specification; Hibernate is the implementation

**JPA** (Jakarta Persistence API) is a set of interfaces and annotations —
`@Entity`, `@Id`, `EntityManager` — with no behavior of its own. **Hibernate** is the
concrete library that actually reads those annotations and talks to a database; it's
Spring Boot's default choice, pulled in transitively by `spring-boot-starter-data-jpa`.
A different provider (EclipseLink) would read the exact same `@Entity` class and behave
the same way from the entity's point of view — this is the same specification/
implementation split lesson 18 described for SLF4J and Logback.

---

## 2. `@Entity` — a class that maps to a table

```java
@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;
    private String author;

    protected Book() { }   // JPA requires this - Hibernate uses it via reflection
    public Book(String title, String author) { ... }
}
```

Starting this lesson with `spring.jpa.hibernate.ddl-auto: update` produces a real,
unedited log line:

```sql
create table book (
    id bigint generated by default as identity,
    author varchar(255),
    title varchar(255),
    primary key (id)
)
```

Hibernate read `@Entity`, `@Id`, and `@GeneratedValue` and created a matching table
**before this lesson's code ever ran** — no SQL was written by hand. `ddl-auto: update`
is convenient for learning and prototyping; lesson 36 replaces it with Flyway, a real
migration tool, because letting Hibernate guess schema changes is not something you want
happening automatically against a production database.

---

## 3. `EntityManager` — the raw JPA API

```java
@PersistenceContext
private EntityManager entityManager;

@Transactional
public Long createBook(String title, String author) {
    Book book = new Book(title, author);
    entityManager.persist(book);
    return book.getId();
}
```

```sql
insert into book (author, title, id) values (?, ?, default)
```

`entityManager.persist(book)` is JPA's raw API for "start managing this new object" —
Spring Data's repositories (lesson 31) are a layer built entirely on top of this exact
API. Seeing it directly first is what makes a repository's `save()` legible later: it
isn't magic, it's this call, wrapped.

---

## 4. The persistence context: a first-level cache

```java
@Transactional
public void demonstrateFirstLevelCache(Long id) {
    Book first = entityManager.find(Book.class, id);   // SQL sent
    Book second = entityManager.find(Book.class, id);  // NO new SQL
    System.out.println(first == second);                // true
}
```

Real output:

```
select b1_0.id, b1_0.author, b1_0.title from book b1_0 where b1_0.id=?
  First find() - SQL was sent
  Second find() - same id, NO new SQL was sent
  first == second (literal same object)? true
```

Only **one** `SELECT` appears in the log, for two `find()` calls. The **persistence
context** — the set of entities a transaction is currently managing — acts as a
first-level cache: asking for the same id again within the same transaction returns the
exact same Java object, with no round trip to the database at all. This cache is scoped
to a single transaction; it isn't shared across requests or threads.

---

## 5. Dirty checking: no `save()` call, and an `UPDATE` still happens

```java
@Transactional
public void demonstrateDirtyChecking(Long id) {
    Book book = entityManager.find(Book.class, id);
    book.setTitle("Effective Java (3rd Edition)");   // no persist(), no merge(), no save()
}
```

```sql
select b1_0.id, b1_0.author, b1_0.title from book b1_0 where b1_0.id=?
  Loaded book, title="Effective Java"
  Changed title in memory - watch for an UPDATE when this transaction commits
update book set author=?, title=? where id=?
```

**A real `UPDATE` fired, with no explicit save call anywhere in this method.** Hibernate
takes a snapshot of a managed entity's state when it's loaded, and — at transaction
commit (or an explicit flush) — compares the entity's current state against that
snapshot. Any difference becomes an `UPDATE`, automatically. This is **dirty checking**,
and it's a genuinely important, sometimes surprising behavior: a managed entity mutated
anywhere during a transaction — including deep inside a method that looks like a
read-only getter chain — can produce a write nobody explicitly asked for. Understanding
this is what makes a later bug ("why did this row change — I never called save!") make
sense instead of feeling like a mystery.

---

## 6. Summary

- **JPA** is the specification (`@Entity`, `@Id`, `EntityManager`); **Hibernate** is
  Spring Boot's default implementation of it — the same relationship as SLF4J/Logback.
- **H2** runs a real SQL database in-process, in memory — no install beyond the JDK,
  used through lesson 36.
- **`ddl-auto: update`** lets Hibernate create/alter tables to match `@Entity` classes —
  convenient for learning, replaced by Flyway (lesson 36) for anything real.
- **`EntityManager.persist`/`find`** are JPA's raw API — Spring Data repositories
  (lesson 31) are built entirely on top of these same calls.
- **The persistence context is a first-level cache**: fetching the same id twice in one
  transaction returns the literal same object, with only one `SELECT` sent.
- **Dirty checking** means a managed entity's field can be mutated with no explicit save
  call, and Hibernate still issues a real `UPDATE` at commit time — a genuinely
  important behavior to understand before it causes a confusing surprise.
