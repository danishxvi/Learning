# 31 · Spring Data repositories

> **Run the code for this lesson**
> ```bash
> mvn -f Spring/05-data-access-with-spring-data-jpa/31-spring-data-repositories spring-boot:run
> ```

Lessons 29 and 30 called `EntityManager.persist`/`find`/`remove` directly. This lesson
replaces all of that boilerplate with a single, empty interface — and proves exactly
what gets injected in its place.

---

## 1. An interface with no implementation, anywhere

```java
public interface BookRepository extends JpaRepository<Book, Long> {
}
```

That's the entire file. No class implements it anywhere in this project. Injecting it
and asking what it actually is:

```java
System.out.println(repository.getClass());
```
```
class jdk.proxy2.$Proxy94
```

**A JDK dynamic proxy**, generated by Spring Data at startup — not a class anyone wrote.
Spring Data reads the `JpaRepository<Book, Long>` type parameters (entity type, id
type), generates an implementation of every method the interface hierarchy declares, and
registers the result as a bean. This is the same "generate an implementation at
runtime" idea lesson 09 saw with `@Configuration`'s CGLIB proxying — a different
mechanism (JDK proxy vs. CGLIB subclass), same underlying pattern: the object you inject
is not the class you wrote, but something built to stand in for it.

`JpaRepository` sits at the top of a small hierarchy: `CrudRepository` (the basic
`save`/`find`/`delete` operations) → `PagingAndSortingRepository` (adds `Pageable`/`Sort`
support, lesson 34) → `JpaRepository` (adds JPA-specific extras, like batch operations).
Extending the top of the chain gets everything beneath it for free.

---

## 2. `save()` — insert *and* update, decided automatically

```java
Book saved = repository.save(new Book("Effective Java", "Joshua Bloch"));  // id == null
```
```sql
insert into book (author, title, id) values (?, ?, default)
```

```java
Book updated = repository.save(new Book(saved.getId(), "Effective Java (3rd Edition)", "Joshua Bloch"));
```
```sql
select b1_0.id, b1_0.author, b1_0.title from book b1_0 where b1_0.id=?
update book set author=?, title=? where id=?
```

**One method, two entirely different SQL outcomes**, decided by whether the entity
passed in already has an id. The second call is not a blind `UPDATE` either — a
`SELECT` runs first. Internally, `save()` calls `entityManager.persist()` for a
brand-new entity (no id) and `entityManager.merge()` for one that already has an id —
`merge()` needs to load the current managed instance first (hence the `SELECT`) before
copying the passed-in object's field values onto it and letting dirty checking (lesson
29) produce the `UPDATE` at flush time.

---

## 3. Everything else, generated the same way

```java
repository.findById(saved.getId());   // Optional<Book> - lesson 23's exact pattern
repository.findAll();                 // List<Book>
repository.count();                   // long
repository.existsById(999L);          // boolean
repository.deleteById(saved.getId()); // void
```

Every one of these produced real, distinct SQL in this lesson's run — a `SELECT ... WHERE id=?`
for `findById`, a bare `SELECT` for `findAll`, `SELECT count(*)` for both `count()` and
`existsById` (the latter with a `WHERE` clause), and a `DELETE` for `deleteById`. None of
it is hand-written — declaring `interface BookRepository extends JpaRepository<Book, Long>`
is the entire implementation effort for all of it.

---

## 4. Why this matters going forward

Nothing about `EntityManager` from lessons 29–30 stopped working or being true — a
`JpaRepository` **is** built on exactly that API underneath. What changed is who writes
the boilerplate: instead of a `@Service` class with `@PersistenceContext` and manual
`persist`/`find`/`remove` calls for every entity, one empty interface per entity type
covers the common cases. Lesson 32 adds the one thing a generated interface can't guess
on its own — queries specific to your domain, driven either by naming convention or a
hand-written `@Query`.

---

## 5. Summary

- **`interface BookRepository extends JpaRepository<Book, Long>`** needs no
  implementation — Spring Data generates a JDK dynamic proxy for it at startup.
- **`JpaRepository` extends `PagingAndSortingRepository` extends `CrudRepository`** —
  each layer adds capability; extending the top gets everything beneath it.
- **`save()`** decides insert vs. update by whether the entity has an id —
  a new entity is `persist()`ed directly; an existing one is `merge()`d, which loads the
  current row first (a real `SELECT`) before the `UPDATE`.
- **`findById`, `findAll`, `count`, `existsById`, `deleteById`** all come for free, each
  producing real, distinct SQL — none of it written by hand.
- Everything here is built directly on top of the `EntityManager` API from lessons
  29–30, not a replacement for understanding it.
